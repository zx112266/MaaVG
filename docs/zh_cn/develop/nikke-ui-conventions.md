# 妮姬（国服 com.tencent.nikke）界面约定

> 坐标空间：720 × 1565（与 `interface.json` 的 `display_short_side: 720` 一致，OCR box 可直接当 roi / click 用）

## 一、最容易搞混的：「公告弹窗」和「公告入口」不是一回事

| 对比项 | 公告弹窗（推送） | 公告入口（按钮） |
|---|---|---|
| 长什么样 | 画面居中一块大面板，盖住标题页 / 大厅 | 标题页**左侧竖列第 1 个**，铃铛图标 + 下方「公告」二字 |
| 文字锚点 | 「活动公告」「系统公告」页签；底部「一周内不再显示」 | 只有「公告」两个字，无页签 |
| 出现时机 | 启动进标题页时、进大厅后自动弹出 | 一直在，静态按钮 |
| 处理方式 | 勾「一周内不再显示」→ 点右上角 × | **不做任何动作** |
| 坐标 | 面板 y 约 380–1120 | 铃铛 ≈(62, 245) |

**硬规则：公告入口只识别、不点击。** 任何脚本里都不允许对 x∈[0,140] ∧ y∈[180,420] 的区域发点击。

## 四、踩过的坑

- 作战出击会被公告弹窗遮挡（弹窗下沿约 y=1275），但底栏（y≈1500）不受影响 → 大厅判据优先用底栏。
- 标题页底部 y>1430 是防沉迷 / 版号法律文本，全屏宽松匹配会误命中。
- 游戏冷启动偶尔卡在资源校验（67% / 22% 等），属游戏行为，等待或强杀重开即可。

## 六、启动脚本的停滞重启设计（2026-11-13 定稿）

- 实测冷启动：StartApp → 15 s 时仍在 `[2/2] 消息同步`，**23 s 才出现「点击开始」**。
- 因此停滞窗口取 **35 s**（23 s + 12 s 余量）；取 20 s 会把正常冷启动误判为卡住。
- 用 `on_error` 而非 `max_hit` 做停滞分支：`max_hit` 只让节点失效、流程空转，`on_error` 才会真正接上重启节点。
- 链路：`启动妮姬 --35s 无命中--> 停滞重启_1(StopApp+3s) → 停滞_重新拉起_1 --35s--> 停滞重启_2 → 停滞_重新拉起_2 --35s--> 停滞放弃`，**最多重启 2 次**。
- `on_error` 语义已用 3~4 s 短超时探针实测：节点序列 `启动 → 重启_1 → 拉起_1 → 重启_2 → 拉起_2 → 放弃` 完全按预期执行。

## 七、大厅判据（2026-11-13 实测提取）

大厅首页的稳定特征（720×1565，OCR box 实测）：

| 锚点 | ROI | 实测 box | score | 弹窗遮挡 |
|---|---|---|---|---|
| 作战出击 | [500,1230,200,90] | [519,1248,160,65] | 0.99995 | 会（弹窗下沿 y≈1292） |
| 方舟 | [520,1090,170,110] | [559,1123,93,60] | 0.9558–0.99994 | 会 |
| 前哨基地 | [100,1230,180,90] | [122,1247,130,60] | 0.99988 | 会 |
| 底栏 妮姬/部队/大厅/物品栏/队员招募 | [60,1480,620,60] | y≈1503 | 0.997–0.9999 | **不会**（y 1500 > 1292） |

**三锚点串联 = 大厅**（`nikke_common.json` 的 `大厅_判据_作战出击 → _方舟 → _前哨基地`），三者同时命中才判大厅，避免在 妮姬/部队/物品栏/队员招募 这些“有底栏但不是大厅”的页面误判。

**不可作判据的变量**：`185K+` / `59670 K`（资源数会变）、`LV.334`（等级会变）、`通关【23-11】`（进度会变）、横幅（前线犒赏 / FIRST LYCORIS PASS / 真彩 Flavor 会轮换）。

复用方式：任何操作后接 `"next": ["回到大厅_确认"]`——它先尝试关活动公告弹窗（3 s 超时），再跑三锚点确认；确认失败走 `大厅_未确认`（StopTask）留下明确节点名。
